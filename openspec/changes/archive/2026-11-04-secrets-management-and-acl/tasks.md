## 2. Shared permission evaluation and audit trail

- [x] 2.1 Implement the permission flags (Read, Write, Create, Delete) and the `IFolderAccess` contract in `Custode.Infrastructure/Access/`, computing effective permissions by walking ancestors from the folder path and stopping at folders that break inheritance (design D3). Verify unit tests for: inherited grant, child grant added, broken inheritance, union of direct and group grants, and no deny (spec: access-control, "Folder permissions are inherited", "A folder can break permission inheritance", "Effective permissions combine direct and group grants").
- [x] 2.2 Implement the folder path normalization utility (absolute, `/` separator, collapsed separators, trailing slash removed). Verify unit tests for `production//aws/` → `/production/aws` and for rejection of relative paths (spec: secret-management, "Folder paths form a normalized hierarchy").
- [x] 2.3 Implement `IAuditTrail` in `Custode.Infrastructure/Audit/`: per-tenant sequence, SHA-256 hash over canonical fields plus the previous hash, and the chain head row with a concurrency token. The entry is added to the same `DbContext` as the action. Verify tests for: sequence increments by one, the hash links each entry to its predecessor, and a failed audit write rolls back the action (spec: security-audit, "Audit entries are written atomically with the action", "Audit entries are chronological within a tenant").
- [x] 2.4 Implement denied-attempt recording: the audit entry is saved in its own transaction, separate from any action. Verify a test where a denied secret read produces a persisted entry with outcome `denied` and no change to any secret (spec: security-audit, "Critical actions produce an audit entry").
- [x] 2.5 Implement chain verification in `IAuditTrail`, returning the entry count on success or the first altered sequence number on failure. Verify a test that alters an audit row by bypassing the trigger in the test database and expects the reported sequence number (spec: security-audit, "Audit entries are tamper-evident").
- [x] 2.6 Implement the operator-only endpoint `POST /api/operator/tenants/{tenantId}/vault` (policy `Operator`, tenant-independent per the tenant-isolation spec). It creates the root folder `/` and the bootstrap grant with all four permissions for the administrator, after checking that the administrator belongs to the tenant. The operation is written under the target tenant's scope with the operator as actor, and is audited as `vault initialized` and `grant set`. Verify tests for: the root folder and four-flag grant, the audit entries and actor, rejection of non-operators (403), rejection of an administrator from another tenant (404), and a second initialization (409) (spec: access-control, "Permissions are granted on folders to users or groups"; tenant-isolation, "Tenant-free operations are explicitly marked"; design D4).
- [x] 2.7 Record an audit entry with outcome `denied` when an application operation tries to update or delete an audit entry, and only then reject the save with `AuditEntryImmutableException`. The attempt is saved in its own transaction, so it survives the rejection. Applies to both the asynchronous and the synchronous save paths. Verify tests on SQLite and PostgreSQL that the attempt is persisted with the target entry and operation, and that the original entry is unchanged (spec: security-audit, "Audit entries are immutable through the application"; design D10).

## 4. Secret management slice

- [x] 4.1 Implement the secret type model and payload protection: username/password requires both values, PAT and API key require one value, file-based requires one file with an allowed extension (`.crt`, `.cer`, `.pem`, `.pfx`, `.p12`, `.key`) and a size within the operator-configured limit. The JSON payload is protected with `ISecretProtector` under the tenant purpose. Verify tests for each type's valid and invalid inputs, and that the stored payload is not equal to the plaintext (spec: secret-management, "Secrets have a supported type", "Username/password...", "Token and API key...", "File-based secrets accept certificate and key files"; secret-encryption, "Secret values are encrypted at rest").
- [x] 4.2 Implement folder create, list, and delete under `Features/SecretManagement/Folders/`. Deletion is rejected while the folder has secrets or subfolders. Verify tests for normalized creation, duplicate rejection, relative path rejection, and non-empty deletion rejection (spec: secret-management, "Folder paths form a normalized hierarchy", "Folders are removed only when empty").
- [x] 4.3 Implement secret create under `Features/SecretManagement/CreateSecret/`, requiring Create on the target folder and returning 404 when the user has no effective permission on it. Verify tests for permitted creation, forbidden creation with Read but not Create, not-found for no permission, and creation in a missing folder (spec: secret-management, "Every secret belongs to exactly one folder"; access-control, "Inaccessible folders and secrets appear as non-existent"). Each creation is audited with no secret value in the entry (security-audit, "Entry content never includes plaintext").
- [x] 4.4 Implement secret listing under `Features/SecretManagement/ListSecrets/`, returning metadata only and requiring Read. Verify a test that listing a folder returns names, types, and timestamps and that no value or file content appears in the response (spec: secret-management, "Secret listings never expose secret values").
- [x] 4.5 Implement the value read under `Features/SecretManagement/ReadSecretValue/`, requiring Read. Verify tests for a successful read, a denied read with Write but without Read returning 403, and a read with no permission returning 404. Verify that both the success and the denial produce audit entries (spec: access-control, "Read permission reads a secret value", "Secret visible without Read"; security-audit, "Secret value read", "Denied secret access").
- [x] 4.6 Implement secret update (Write) and delete (Delete) under `Features/SecretManagement/UpdateSecret/` and `Features/SecretManagement/DeleteSecret/`, each audited. Verify tests for permitted and forbidden updates and deletes, and that a denied update leaves the value unchanged (spec: access-control, "Permission levels are Read, Write, Create, and Delete").
- [x] 4.7 Implement secret move under `Features/SecretManagement/MoveSecret/`, requiring Delete on the source and Create on the destination. Verify tests for a permitted move and for a move where Create on the destination is missing, which leaves the secret in its original folder (spec: secret-management, "Secrets can be moved between folders").
- [x] 4.8 Verify that logs and exception messages produced by the secret slices contain identifiers only. Add a test that captures logs during create, read, update, and move and asserts that no secret value or file content appears (spec: secret-encryption, "Secret value in logs"; design D8).
